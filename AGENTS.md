# WACheap: agent notes

Official WhatsApp Cloud API broadcast and shared inbox for Indonesian online sellers (first niche). The customer brings their own
number and pays Meta's rate with no markup and no per-seat fees. AGPL-3.0, self-hostable. The v1 spec lives in atur:
workspace `joyodigitama`, project WAB (`c512662b-4342-4ce2-bf68-da11142eccf0`), page "WACheap v1 spec". File work there.

## Stack (same as joyorogo)

Better-T-Stack monorepo (`bts.jsonc`): bun workspaces + turborepo, Hono on Cloudflare Workers (`apps/server`), oRPC
procedures in `packages/api` (served as RPC at `/rpc` and OpenAPI at `/api-reference`), Drizzle 0.45 on D1
(`packages/db`), better-auth (`packages/auth`), TanStack Router + Tailwind 4 + shadcn/base-ui web app (`apps/web`,
`packages/ui`), varlock for env (`.env.schema` per package), Alchemy for deploys (`packages/infra/alchemy.run.ts`),
oxlint + oxfmt. Library versions are pinned to joyorogo's in the root catalog; keep them in step.

Cloudflare pieces (declared in `packages/infra/alchemy.run.ts`):

- `BROADCAST_QUEUE` (queue `broadcast`, dead letters in `broadcast-dlq`): the API enqueues `BroadcastJob`s
  (`packages/api/src/lib/broadcast-job.ts`, at most 50 recipients each); `apps/server/src/queue.ts` consumes them.
- `INBOX` (Durable Object `InboxRoom`, `apps/server/src/inbox-room.ts`): hibernating WebSockets at `/api/inbox/ws`;
  `publish(event)` fans an event out to every open tab. Conversations themselves live in D1.
- Still to come: an MCP endpoint whose tools call the same oRPC procedures as the dashboard (WAB-12).

## Alchemy runs under Node

`packages/infra` scripts start the CLI with `env -u npm_execpath node .../alchemy/bin/cli.js`. Under bun, alchemy
2.0.0-beta.84/85 loads its `src/` and then spawns the Vite child with `bin/register-dev-mode.js`, which the published
package leaves out, so the web app never starts. Keep that form (also in `deploy.yml`) until an alchemy release fixes it.
Alchemy also refuses drizzle-kit 0.x's `meta/_journal.json` layout: `bun run db:generate` writes to
`packages/db/src/migrations` and copies the `.sql` files to `packages/db/migrations-deploy`, which is what D1 applies.
Commit both. The root `overrides` pins `@effect/platform-node-shared` to the installed effect version; without it
alchemy cannot load `@effect/platform-bun`.

## Typechecking uses tsrs, not tsc

`check-types`, `postinstall` and CI run `tsrs` (pinned in the root `package.json`): `tsrs --noEmit` to check,
`tsrs -b` for the project-reference packages (api, auth, db) that write `.d.ts` to `dist/`. Never run bare `tsrs` or
`tsrs -p .` in an app: without `--noEmit` it emits JS. Apps read API types from `packages/api/dist` (gitignored); after
changing api, db or auth, run `bunx tsrs -b packages/api` (or `bun run dev:types`). `apps/web/src/routeTree.gen.ts` is
generated by the vite build, so build before typechecking web.

## D1 limits: bounded statements, tests on the guarded database

D1 refuses more than 100 bound parameters per statement (also 100 KB of SQL, 2 MB per value, 50-byte LIKE patterns);
local SQLite allows 32766, so a caller-sized query passes every local test and fails in production. Contact imports and
broadcast recipient lists are exactly that kind of query. Tests get their database from `d1TestDb()` in
`@wacheap/db/test-d1` (never `createClient`), which throws what D1 throws. Caller-sized work goes through
`packages/api/src/lib/d1.ts` (`insertChunked`, `readChunked`, `chunk`).

## WhatsApp numbers and webhooks

Two ways to connect a number (`wa_number.source`):

- `embedded`: Meta's Embedded Signup v4, the "Hubungkan dengan Facebook" button (`whatsapp.numbers.connectEmbedded`,
  `apps/web/src/lib/facebook-signup.ts`). The FB.login code becomes the seller's business token for this server's own
  Meta app (META_APP_ID, WHATSAPP_SIGNUP_CONFIG_ID, META_APP_SECRET). A number not yet on Cloud API is registered with
  a random PIN, stored sealed (`pin_sealed`). Webhooks arrive at `/api/whatsapp/webhook` (META_APP_SECRET,
  WHATSAPP_VERIFY_TOKEN), routed by phone_number_id; no override. Its app secret is read from config, not the row.
  Until App Review grants advanced access, only people with a role on the Meta app can complete the flow.
- `manual`: WABA ID, phone number ID, a system-user token and the secret of the token's own Meta app. Each such number
  gets `/api/whatsapp/webhook/<webhookKey>`, registered with Meta as a phone-number override and verified with that
  number's app secret; requests there may only touch the same user's numbers. For self-hosters and developers.

Switching a number between the two cleans up after the old one (clears the manual override, or unsubscribes this
server's app from the WABA when no other embedded number needs it). Tokens, app secrets and PINs are AES-GCM sealed
(`packages/api/src/lib/whatsapp/seal.ts`, key from BETTER_AUTH_SECRET); every Graph call carries appsecret_proof.
Template and account webhooks ignore overrides: poll Graph for template status. `message` is unique on
(number_id, wa_message_id), never on the wamid alone: a seller signs their own webhooks.

## Meta rules that shape the code

- Message fees are billed by Meta to the customer's own WABA. We never resell or mark up messages.
- Rates change often: keep them in config/data with an effective date, never as constants in code.
- Opt-in is enforced; opt-out keywords (STOP, BERHENTI) are handled before any send.

## Commands

- `bun run dev`: Alchemy dev (server on :3000, web on :3001)
- `bun run check-types`, `bun test packages/api/src`, `bun run check` (oxlint + oxfmt)
- `bun run db:generate`: drizzle migration from `packages/db/src/schema`
- `bun run deploy`: Alchemy deploy to your personal stage (D1 migrations are applied on deploy). Production deploys
  run from `.github/workflows/deploy.yml` on push to master once the repo variable `DEPLOY_ENABLED` is `true`; the
  secrets it needs are listed at the top of that file.
